# MentalCream 프로젝트 분석 및 총평

작성일: 2026-08-30  
분석 기준: `v2` 브랜치

## 1. 한 줄 평가

MentalCream은 단순 기록 CRUD를 넘어 사용자의 기분·에너지·고민·완료 활동을 축적하고, 이를 통계와 AI 행동 추천으로 연결한 개인화 멘탈 관리 서비스다. 현재 수준은 **주니어 개발자의 백엔드·DB·AI API 연동 역량을 함께 보여줄 수 있는 설득력 있는 포트폴리오**에 가깝다. 다만 운영 서비스라고 부르기 위해서는 DB 마이그레이션 자동화, 예외 응답 정교화, 테스트 확대, 배포·관측 체계가 추가로 필요하다.

## 2. 해결하려는 문제와 서비스 가치

취업 준비나 장기 프로젝트 과정에서 사용자는 불안 때문에 계획을 크게 세우고, 달성하지 못하면 다시 자책하는 흐름에 빠지기 쉽다. MentalCream은 이 문제를 다음 순환 구조로 다룬다.

1. 오늘의 기분, 에너지, 고민을 짧게 기록한다.
2. 실제로 완료한 작은 행동을 기록한다.
3. 누적 기록에서 에너지 변화와 활동 패턴을 분석한다.
4. 현재 상태에 맞는 다음 행동 하나를 AI가 제안한다.
5. 통계, XP, 연속 기록으로 사용자가 변화 과정을 확인한다.

서비스의 핵심은 AI 채팅 자체가 아니라 **사용자 행동 데이터와 AI 추천을 연결하는 폐쇄형 피드백 루프**에 있다. 이 점이 일반적인 API 호출 데모와 구분되는 가장 큰 장점이다.

## 4. 현재 구조

요청 처리 흐름은 일반적인 계층형 Spring 애플리케이션 구조를 따른다.

```text
Browser
  -> Spring Security
  -> Controller
  -> Service
  -> JPA Repository / MyBatis Mapper
  -> Oracle
                   -> Gemini API
```

주요 책임은 다음과 같이 나뉜다.

- `AuthService`: 계정 생성과 비밀번호 암호화
- `CurrentUserService`: 인증 정보와 DB 사용자를 연결
- `TodayService`: 현재 사용자의 일일 기록과 완료 활동 관리
- `SuggestionService`: 사용자 기록 분석과 AI 추천 생성 총괄
- `StatsService`: 주간 통계 조립
- `EnergyPatternAnalyzer`: 에너지 변화 기반 카테고리 분석
- `SuggestionPolicyEngine`: 동일 카테고리 추천 반복 제한
- `RecoveryIndexCalculator`: 활동 품질, 에너지 추세, 기록 공백을 점수화
- `StatsMapper`: Oracle 집계 SQL 수행

서비스 컴포넌트를 분석·정책·계산 역할로 나눈 것은 추천 로직이 하나의 거대한 서비스 메서드로 커지는 것을 막는 좋은 선택이다.

## 5. v2에서 개선된 핵심

### 사용자 인증과 데이터 격리

- `app_user` 엔티티와 회원가입 기능 추가
- BCrypt 기반 비밀번호 저장
- Spring Security 폼 로그인과 로그아웃 적용
- 상태 변경 요청에 CSRF 토큰 적용
- 일일 기록, 완료 활동, AI 추천, 통계를 `user_id` 기준으로 분리
- 다른 사용자의 완료 활동 삭제 방지
- 사용자별 동일 날짜 기록과 추천을 한 건으로 제한

이 변경으로 프로젝트가 개인용 데모에서 다중 사용자 서비스 구조로 발전했다.

### 개인화 AI 추천

추천 생성은 다음 데이터를 사용한다.

- 전날의 기분과 에너지
- 고민 내용과 고민 강도
- 사용자가 완료한 활동
- 최근 에너지 평균
- 활동 카테고리별 다음 날 에너지 변화
- 최근 추천 카테고리 반복 여부

에너지가 매우 낮거나 활동이 없는 날에는 무리한 도전을 추천하지 않고 회복 행동으로 전환한다. AI 응답 실패 시 기본 추천으로 대체하는 것도 서비스 중단을 피하기 위한 적절한 방어 로직이다.

### Oracle 활용

단순 저장은 JPA로 처리하고, 복잡한 집계는 MyBatis와 Oracle SQL로 분리했다.

- 카테고리별 XP 합산
- 오늘 또는 어제부터 이어지는 연속 활동 일수
- 전반부·후반부 에너지 변화와 기록 공백을 이용한 회복 지수
- 활동 카테고리별 다음 날 에너지 상승 폭
- 고민 강도 감소 추이

이 구성은 JPA만 사용한 CRUD 프로젝트보다 SQL 활용 역량을 더 분명하게 보여준다.

## 6. 잘된 점

### 6.1 문제 정의와 기능이 연결돼 있다

기록, 추천, 통계가 서로 분리된 기능 목록으로 존재하지 않고, 사용자가 통제감을 회복한다는 하나의 목표로 연결돼 있다. 포트폴리오 설명과 면접 답변을 만들기 좋은 구조다.

### 6.2 AI가 사용자 데이터의 소비자다

AI API를 단순히 호출하는 것이 아니라 서버가 사용자 데이터를 선별하고 정책을 적용한 뒤 프롬프트에 전달한다. 따라서 “AI 모델 연동 및 활용 경험”을 설명할 때 API 호출보다 데이터 흐름, 실패 대응, 추천 정책을 중심으로 말할 수 있다.

### 6.3 사용자 격리가 서비스 전 계층에 반영됐다

엔티티에 `user_id`만 추가한 것이 아니라 Repository 메서드, MyBatis SQL, 통계, 추천 이력, 삭제 검증까지 사용자 조건이 전달된다. 다중 사용자 전환에서 가장 중요한 부분을 제대로 다뤘다.

### 6.4 기술 선택에 역할이 있다

JPA와 MyBatis를 함께 사용한 이유가 비교적 명확하다. JPA는 관계와 일반 CRUD에, MyBatis는 Oracle 집계 SQL에 사용한다. 두 기술을 사용했다는 사실보다 역할 분리 근거가 있다는 점이 좋다.

### 6.5 최소한의 보안 기준을 갖췄다

비밀번호를 BCrypt로 해싱하고 CSRF를 유지했으며, 비인증 API를 차단한다. DB 관리자 계정 대신 애플리케이션 전용 Oracle 계정을 사용하고 비밀값도 환경 변수로 분리했다.

| 평가 영역 | 점수 | 판단 |

| AI 활용 | 4.0 | 사용자 데이터를 반영하고 실패 대체 로직을 보유 |
| 인증·보안 | 3.5 | 기본기는 갖췄으나 OAuth, 권한 세분화, 세션 정책은 추가 가능 |
| 테스트 | 3.0 | 핵심 단위·인증 테스트는 있으나 격리 및 Oracle SQL 테스트가 부족 |
| 배포·운영 | 2.0 | 로컬 실행은 가능하지만 자동 배포와 관측 체계가 없음 |
| 문서화 | 3.5 | DB 전환과 프로젝트 분석 문서는 있으나 루트 README 정리가 필요 |

종합적으로는 **기능 구현 단계는 넘어섰고, 운영 품질을 보강하기 시작해야 하는 단계**다.

4. 배포 환경별 설정을 `local`, `test`, `prod` 프로필로 분리한다.

## 10. 카카오 로그인 추가에 대한 판단

카카오 로그인은 사용자 접근성을 높이고 OAuth2 경험을 보여준다는 점에서 좋은 다음 기능이다. 다만 버튼부터 추가하기보다 계정 모델을 먼저 다음 형태로 확장해야 한다.

- 로그인 제공자: `LOCAL`, `KAKAO`
- 제공자 사용자 ID
- 이메일은 선택 정보로 취급
- 동일 사용자의 로컬 계정과 카카오 계정 연결 여부
- 카카오에서 이름이나 프로필 제공 동의를 철회했을 때의 처리

현재 프로젝트에서는 데이터 격리와 로컬 인증이 먼저 완성됐으므로 카카오 OAuth2를 추가하기 좋은 시점이다. 그러나 채용 포트폴리오의 우선순위만 보면 OAuth 기능 하나보다 **사용자 격리 통합 테스트와 DB 마이그레이션 자동화**가 백엔드 완성도를 더 크게 높인다.

## 11. iMBC 지원 관점에서 강조할 내용

이 프로젝트는 프론트엔드 결과물만 강조하기보다 다음 백엔드 경험으로 설명하는 것이 적절하다.

- 외부 Gemini API를 서비스 로직에 연동하고 실패 시 기본 응답으로 대체한 경험
- 사용자 상태와 행동 이력을 프롬프트에 반영해 개인화 추천을 만든 경험
- JPA와 MyBatis를 역할에 맞게 병행한 경험
- Oracle 집계 SQL로 통계와 패턴 분석을 구현한 경험
- 단일 사용자 구조를 다중 사용자 구조로 전환하면서 전 계층의 데이터 격리를 적용한 경험
- Spring Security, BCrypt, CSRF로 인증의 기본 보안 요건을 적용한 경험
- 구조 변경을 별도 `v2` 브랜치에서 진행하고 테스트와 스키마 문서를 함께 관리한 경험

면접에서는 “Gemini를 사용했다”에서 멈추지 말고 다음 흐름으로 말하는 편이 강하다.

> 사용자별 기록을 DB에 축적하고, 최근 에너지와 완료 활동을 분석한 뒤 정책 엔진으로 추천 범위를 결정했습니다. 그 결과를 Gemini API에 전달해 개인화 문구를 생성했으며, 외부 API 실패 시에도 서비스가 중단되지 않도록 기본 추천으로 대체했습니다. 이후 로그인 기능을 추가하면서 JPA 조회와 Oracle 집계 SQL 전체에 사용자 조건을 적용해 데이터 격리를 보장했습니다.

## 12. 최종 총평

MentalCream의 가장 좋은 점은 기술을 나열하기 위한 프로젝트가 아니라는 것이다. 사용자 기록, SQL 분석, 정책 로직, AI 추천, 통계가 하나의 문제 해결 과정으로 이어진다. 특히 v2의 다중 사용자 전환은 백엔드 개발자로서 데이터 소유권과 보안을 고민했다는 증거가 된다.

현재 프로젝트는 채용 포트폴리오로 충분히 활용할 수 있다. 다음 단계에서는 기능 개수를 늘리기보다 테스트, 마이그레이션, 예외 처리, 실행 문서를 강화하는 것이 좋다. 이 네 부분이 보완되면 “작동하는 개인 프로젝트”에서 “운영을 고려한 서비스 설계 경험”으로 평가 수준이 올라갈 것이다.
